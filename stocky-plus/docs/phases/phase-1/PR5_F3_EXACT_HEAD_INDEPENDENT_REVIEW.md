## 5. Component verdicts

### 5.1 JSONL completeness (C1 / `F-CLAUDE-PR5F3EC-02`) — PASS

`ingest/counts.ts` gates both count tokens on `/^[0-9]+$/` before any exact
string comparison against `bigint.toString(10)`. `jsonl-stream.ts:73-82`
validates before reading a single byte and returns
`count_token_missing_or_malformed`.

Independently falsified (probes A1–A6, B1–B12, 18 assertions):

- JavaScript `$` without `/m` does **not** match before a trailing newline, so
  `"123\n"` is rejected — the Python-style trailing-newline bypass does not exist.
- 26 non-conforming shapes rejected: empty, whitespace-padded, signed, decimal,
  exponent, hex, binary, separators, Arabic-Indic / Devanagari / full-width
  digits, `Infinity`, `NaN`, and non-string inputs.
- No JS numeric coercion: `Number("9007199254740993") === 9007199254740992`, yet
  `compareUnsignedCountToken("9007199254740993", 9007199254740992n)` fails and
  `(…, 9007199254740993n)` passes.
- Transport EOF alone never yields COMPLETE — a 2-object stream against a
  declared count of 3 returns `object_count_mismatch`; matching object count with
  a wrong root count returns `root_object_count_mismatch`.
- Mid-line truncation → `malformed_jsonl`; abort → `stream_aborted`; source throw
  → `stream_aborted`; unknown GID → `unknown_jsonl_identity` (no silent skip that
  could rebalance the counts); oversized line → `stream_truncated`.
- An incomplete or unproven domain cannot become SUCCEEDED: `catalog-sync.ts:544`
  returns PARTIAL_FAILURE for any `streamed.status !== "COMPLETE"` **before**
  `nominateAbsenceCandidates` and `completeSyncRunAndCursor` are reached.

`F-CLAUDE-PR5F3EC-02` is confirmed as the completeness count-token requirement
(not a lock/capacity finding). The `502b869e…` labelling correction is accurate.

### 5.2 Checkpoint / resume — PASS

Paired `(bulkOperationGid, jsonlCommittedLineOrdinal)`; the ordinal is 1-based
and enforced in code (`requireOrdinal`) and by the DB CHECK
`SyncRun_jsonlCommittedLineOrdinal_check` (verified `convalidated = t`).
`deriveIngestBatchId` is a SHA-256 over
`(version, syncRunId, bulkOperationGid, startLineOrdinal)` with 1-based ordinal
validation.

Resume re-streams the signed URL from byte 0 and filters `ordinal > checkpoint`
— there is no HTTP Range or byte-seek dependence (R-146). Batch order is
apply → project → acknowledge, so a crash before acknowledge re-applies lines
that are idempotent under the canonical clock, and a crash after apply never
advances authority past uncommitted data.

Probes K1–K7 on real PostgreSQL: mismatched GID rejected; backward movement
rejected; five identical acknowledgements converge on one value; `0`, `-1`,
`1.5`, `NaN`, `2^53` all rejected in code and `0` also rejected by the DB CHECK;
attaching a new GID nulls the ordinal and the persisted counts; a foreign
`shopId` cannot advance another shop's checkpoint. Probe B9 shows ordinals are
byte-boundary independent across chunk sizes 1/3/7/13/64/4096 with CRLF endings,
and B10 shows a missing trailing newline still yields the final line exactly once.

### 5.3 Bulk operation lifecycle — PASS

Pre-submit intent (`persistBulkSubmitIntentAndFence` writes `bulkSubmitIntentAt`
+ `bulkQueryFingerprint` + fence generation) precedes `bulkOperationRunQuery`.
On an uncertain submit the next step takes the recovery branch and never
resubmits: `recoverOrphanBulkOperation` reads `bulkOperations(first: 25)`,
matches on exact query fingerprint within `[intent−5s, intent+120s]`, adopts on
exactly one match, and returns `FAILED_CLOSED` on ambiguity. Polling is
`bulkOperation(id:)` only — `currentBulkOperation` is deleted from
`shopify-gql.server.ts` and is rejected by the GraphQL AST scanner in both the
read contract and the excepted mutation module (probe C7).

`canonicalSuccessEligible` requires `COMPLETED && url && partialDataUrl == null`,
so `partialDataUrl` can never become canonical success (R-129).
`bulk_operations/finish` is `CONTROL_ONLY` in `execution-strategy.server.ts` and
`signalBulkOperationContinuation` only sets `nextEligibleAt` on `RETRY_WAIT`
jobs — it applies no facts and cannot become a second fact applicator.

Shopify's five-concurrent-bulk-operation limit is respected by topology: domains
run sequentially within `runCatalogFactsSyncStep`, one SyncRun per (shop, domain,
correlationId), and the only other producer is `inventory-state-reconcile`.
Worst case is 2 concurrent operations per shop.

### 5.5 Absence / deletion / revival — PASS

Nomination and confirmation are distinct functions.
`nominateAbsenceCandidates` derives candidates only from proven owning-domain
evidence (`lastSeenFullSyncRunId != epochId` **and** `existenceRequestGen <= fence`)
and is called only after `streamed.status === "COMPLETE"` (bulk domains) or a
complete `readAllLocations` — an incomplete epoch cannot generate absence. A
circuit breaker holds when the candidate count exceeds both an absolute floor
(250) and a proportion of LIVE rows (200 bps), marking `CIRCUIT_BREAKER_HELD`
(R-154). Nomination always returns `deletionReconciliationHealthy: false`.

`FEATURE_PR5_ABSENCE_TOMBSTONE` defaults false in `feature-flags.server.ts`,
`.env.example`, and CI. The gate is read immediately before the destructive
transition; probe G1 confirms a CONFIRMED-ABSENT identity is not tombstoned with
the flag off, and probe G2 confirms a FAILED confirmation is never treated as
absence. Ordinary canonical apply performs no physical DELETE — `writers.ts` is
INSERT/UPDATE only and historical identity is preserved via `deletedAt` /
`deletionSource` columns.

### 5.6 Product revival (`NEW-CLAUDE-F2CCM-01`) — PASS

`apply/existence.ts` is unchanged from `main`; the two-confirmation protocol was
already landed and F3 does not weaken it. Probes F1–F4 attempted to falsify it:

- One LIVE observation on a terminal Product returns
  `terminal_first_confirmation`, `mutate: false`, and only records the interval.
- A second confirmation that overlaps the first
  (`incoming.requestGen <= first.responseGen`) returns
  `terminal_overlapping_confirmations`, `mutate: false` — tested at
  `(20,31)`, `(25,35)`, `(29,40)`, `(30,41)` against a stored `(20,30)`.
- Only a strictly non-overlapping second confirmation (`31,32`) revives.
- `createdAt` mismatch blocks revival even with two confirmations.

Retry budgeting: `MIN_PRODUCT_REVIVAL_OBSERVATION_CYCLES = 2` and
`shouldRetryCompatibilityProjection("canonical_product_not_live", n)` is `true`
for n = 0 and 1, `false` at n = 2 — at least two complete observation cycles are
allowed before exhaustion. See P3-CLAUDE-F3XH-03: the guard's return value is
discarded at the single production call site, so the invariant currently holds
because nothing exhausts rather than because the budget is enforced. This cannot
cause premature exhaustion.

### 5.7 Compatibility projection — PASS

Canonical commit remains authoritative. `markCompatibilityProjectionPending`
runs **inside** the canonical transaction whenever existence, attributes,
presence, or a diagnostic changed, and the migration makes `PROJECTION_PENDING`
the column default for all five fact tables — so a row is pending by
construction until a projector proves it. Projection then runs post-commit.

`projectAppliedCanonicalFacts` flips to HEALTHY only when
`status === "SUCCEEDED" && !hasMore && !resolved.truncated`; a truncated child
page or a `hasMore` result returns `{...result, hasMore: true}` and leaves the
existing PROJECTION_PENDING evidence authoritative. Failure writes DEGRADED and
never rolls back canonical facts — `catalog-sync.ts:513-522` swallows projection
errors (re-throwing only `shop_processing_disabled`) and, critically, does not
acknowledge the checkpoint differently. Both PENDING and DEGRADED are counted as
health evidence by `readCatalogHealthEvidence`. F2C core does not become the
owner of F3 health state: `writeCompatibilityProjectionState` is called only from
the F3 projector, and the F2C isolation test was retargeted onto
PROJECTION_PENDING rather than relaxed. Cross-tenant projection isolation is
preserved (all reads go through `createTenantDb`).

### 5.9 Capacity / concurrency (`F-CLAUDE-PR5F3EC-01`) — PASS

`deriveCanonicalWriterConcurrency` computes exactly
`D * max(B, Σ canonical-writer concurrency)`. Probe D1 confirms the `max` is
load-bearing: with D=3, B=2, Σworkers=6 the result is 18, not `D*B = 6`.

The worker sum is derived from the real queues, not a literal.
`app/jobs/worker-concurrency.ts` is the single source of truth, and
`queue.server.ts:293,300` construct the only two BullMQ Workers in the codebase
(`grep "new Worker"` finds exactly two production sites) from those same
constants. Probe D2 asserts
`cfg.aggregateWorkerConcurrency === WEBHOOK_WORKER_CONCURRENCY + CRON_WORKER_CONCURRENCY`
and that understating `B` cannot push the envelope below the worker sum.

Configuration cannot silently understate concurrency: `positiveSafeInteger`
rejects `0`, `-1`, `1.5`, `abc`, empty, `" 1"`, `"+1"`, `"1e3"`, `"0x10"`,
`2^53`, and `"9007199254740993"` (probe D3), and the derived product fails closed
outside the safe-integer range (probe D4). An envelope that cannot fit one
identity raises `CanonicalLockCapacityInsufficientError` rather than silently
reducing to zero (probe D5), and raising concurrency monotonically shrinks the
effective batch while preserving `batch × concurrency <= conditionBBudget`
(probe D6).

Race AW is genuinely tested: `pr5-f3-lock-capacity-aw.test.ts` evaluates the real
disposable PostgreSQL settings, 12/12 passing at CI-equivalent settings.

### 5.10 Locking — PASS

`pg_advisory_xact_lock` only; the session-scoped spelling is forbidden and
`foundation-safety.test.ts` asserts its absence across both production roots.
The CTE + `CAST(... AS INTEGER)` form selects the two-key int32 signature.

Advisory locks are the first-insert anchor (R-160): `acquireOrderedLocks` runs
before the canonical row is read or inserted, so a nonexistent row is still
serialized. Multi-identity ordering is deterministic and caller-independent:
`orderCanonicalLockKeysForAcquisition` dedupes then sorts ascending on
`(key1, key2)` derived from SHA-256 of a length-prefixed preimage. Probe E1
shuffled 40 identities 25 times and got an identical acquisition order every
time — so the JSONL path's line-order grouping and the reconcile path's
`localeCompare` grouping cannot deadlock against each other. Probe E2 confirms a
total order with dedupe, E3 confirms identical Shopify GIDs in different shops
never share a key, E4 confirms the length-prefixed encoding resists
component-boundary confusion, and E5 confirms 1,000 keys are all valid signed
int32.

No Shopify or network call occurs while canonical locks are held. The
`isSharedLockResourceFailure` sub-batch fallback re-enters
`applyCanonicalFactsWithRetry` with the reduced size, so capacity is re-evaluated
— it never falls back to an unanchored path, never advances the cursor past
unapplied groups, and aborts with `canonical_lock_capacity_retry_exhausted`
rather than proceeding unsafely.
